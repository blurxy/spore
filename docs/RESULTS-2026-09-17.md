# First run on real hardware — 2026-09-17

The first time SPORE has run on anything but a laptop. One Android tablet, one Windows laptop,
one 5 GHz AP. Commit `1558262`, 119 tests.

Everything in `ARCHITECTURE.md` §3.1 up to this point rested on a laptop simulation.

## Step 0 — the suite on Android: **119 / 119, zero failures**

```
ℹ tests 119   ℹ pass 119   ℹ fail 0   ℹ duration_ms 3570
npm test  9.08s user  232% cpu  4.177 total
```

This is the version check that means anything. BLAKE2b, ed25519, the Noise handshake, the
substrate, the scheduler, the R7 claim witness and both retention bounds landed the same day —
all verified on an ARM phone SoC. Nothing in this repo is platform-specific by intent, and that
intent is now tested rather than asserted. The suite parallelises across the tablet's cores
(232% CPU) and runs in 3.6 s against roughly 2 s on the laptop.

## Step 2 — discovery: **multicast works on Android**

The runbook flagged this as a live risk: Termux has no `MulticastLock`, so a phone may transmit
HELLO and never receive one. On this device it receives.

```
tablet:   42ms  beacon.peer   {sporeId: 23c79d54...}
tablet: 3425ms  beacon.peer   {sporeId: 80a410f7...}   <- the laptop's announce, received
laptop:   26ms  hypha.established
```

The tablet learned about the laptop from multicast, not from a unicast reply — so
`MulticastLock` is not required on this device/ROM. **This does not generalise.** It is one
tablet on one ROM; the `--dial` path exists precisely because the next device may differ.

## Step 3 — the tablet's uplink, alone

400 blocks, 12.60 MB, tablet seeds, laptop joins, `--sources 1`. All runs: **400/400 linked,
0 noblock, 0 timeout, 0 released, 100% attributed to a single source.**

| trial | elapsed | throughput | notes |
|---|---|---|---|
| 1 | 1.13 s | **11.14 MB/s** | clean |
| 2 | 1.44 s | 8.77 MB/s | **contaminated** — 2 seeders |
| 3 | 2.44 s | 5.17 MB/s | **contaminated** — 3 seeders |
| 4 | 1.67 s | **7.55 MB/s** | clean |
| 5 | — | — | no seeder up in time; discarded |
| 6 | 0.92 s | **13.66 MB/s** | clean |

**Trials 2 and 3 are mine, not the mesh's.** Each seeder was started with a 45–110 s timeout
while trials were launched ~12 s apart, so seeders from earlier trials were still running and
competing for CPU and radio. The monotonic decline 11.14 → 8.77 → 5.17 is exactly what one,
two and three competing seeders look like, and it is recorded rather than deleted because a
clean-looking downward curve is precisely the shape someone would later mistake for a finding.
`ps -ef | grep node` on the seeder between trials is now the rule.

**Valid measurement: 7.55 – 13.66 MB/s, three clean trials, mean ≈ 10.8 MB/s.**

## What this establishes

- **The stack runs on Android.** 119/119, unmodified.
- **Multicast discovery works there**, on this device.
- **One source delivered 7.5–13.7 MB/s over 5 GHz** for this workload. Read that as *what one
  source delivered through `sync.js` as shipped*, **not** as the tablet's radio throughput —
  see the caveat below, added after an advisor pass found a ceiling in our own request path
  that sits inside the measured range.
- ~~§3.1's uplink constant is conservative but inside the measured range; the model is not
  wrong here, it is pessimistic by up to 1.8×.~~ **Withdrawn.** That was an interpretation, not
  a measurement, and the arithmetic below makes it more likely wrong than right.
- **Wi-Fi variance is ~1.8× run to run** even with one seeder, a quiet device, the radio pinned
  out of power-save, and zero packet loss. Any future claim about a curve needs several trials
  per point, not one.

## The number above may be our own request window, not the radio

Added 2026-09-17 after the run, by advisor review of the request path. **This does not retract
the measurement — it questions what the measurement is of**, which is a different and more
uncomfortable thing.

One BLOCK on the wire is 33,100 B (1 + 3 + 32 + 4 + 4 + 260 cert + 32,768 body + 24 AEAD + 4
length). `MAX_INFLIGHT_PER_PEER` is **6**, so at most **198,600 B** is in flight to one source
at a time. That alone caps a single source at:

| idle RTT | window ceiling |
|---|---|
| 5 ms (our measured min) | 37.9 MiB/s |
| 9 ms (our measured mean) | **21.0 MiB/s** |
| 17 ms (our measured max) | **11.1 MiB/s** |

Our three clean trials — 7.55 / 11.14 / 13.66 MiB/s — correspond to *loaded* RTTs of 25 / 17 /
14 ms, which is ordinary Wi-Fi behaviour under a 200 KB burst. **Every measured value sits
inside the window ceiling rather than near any radio limit**, and the ~1.8× variance I recorded
as Wi-Fi noise is exactly what RTT jitter against a *fixed* window produces.

**The model could not have caught this.** `bench/curve.js` uses `RTT_MS = 3`, where the window
bound is ~63 MiB/s — far above anything it simulates. So the simulation and the hardware agreed
with each other while measuring different quantities, which is the worst way for two numbers to
agree. `design-sharding` §5 specified an in-flight depth up to 16 over 256 KiB blocks; what
shipped has roughly 8× less outstanding.

**What would settle it.** Sweep block size — `bench/mesh.js` already takes `--bytes`, and 65,208
is the largest that fits `MAX_BODY`. A window bound predicts throughput scaling roughly with
block size; a radio bound predicts flat. **That test is confounded and should be read carefully:**
bigger blocks also reduce per-byte CPU on the joiner (pure-JS BLAKE2b over the payload, one
ed25519 verify per block), so a speedup at 65,000 does not cleanly separate window from CPU.
Making `MAX_INFLIGHT_PER_PEER` injectable and sweeping *that* at fixed block size is the clean
discriminator, and is about five lines.

Until one of those runs, the honest statement is the one at the top of this section: this
document measured a delivery path, and the radio's share of it is unknown.

## What this does NOT establish, and must not be claimed

- **The knee.** §3.1 predicts it at N=4, from one uplink at ~7.5 MB/s against a P2P-effective
  cell of ~25 MB/s. With one seeder the joiner sees `min(1 × uplink, cell)` and **the cell term
  never appears**. Two devices cannot find a knee. This run de-risks the four-device run; it
  does not substitute for it.
- **The cell constant.** Untouched. Nothing here saturated anything.
- **Anything about phones generally.** One tablet, one ROM, one AP, one direction.
- **Phone-to-phone.** Not tested — this was tablet-to-laptop, and `beacon.js` answers a heard
  HELLO with a unicast reply, so a laptop in the pair can mask a receive-side multicast failure.
  The runbook's step 2 ordering exists for exactly this and still needs a second phone.

## Confounds removed before measuring, and one found during

Wi-Fi power saving was parking the radio between packets: ICMP averaged **86 ms** on a 5 GHz
LAN with 0% loss. `iw dev wlan0 set power_save off` took it to **9 ms** (min 5, max 17). Left
on for the duration and turned off afterwards — it does not survive a reboot or a Wi-Fi
reconnect. Without this the uplink would have read as a slow radio rather than as a power
setting, and the number would have been wrong in a way nothing in the output would reveal.

The confound found during the run was the leftover-seeder contamination above. Both are the
same lesson: the harness reports what it measured, and what it measured is whatever the device
was actually doing.

## Two findings from the same advisor pass, recorded here so they are not lost

Neither is fixed. Both are written down because a finding that lives only in a conversation is
a finding that gets rediscovered.

**1. Two frames, ~10 KB, freeze the spore.** `MAX_SEQ` was lowered to 2^20-1 to bound the
`Bitfield` a peer's claimed seq allocates. It bounded that one and not the *other* thing sized
by the same attacker-chosen number: `FetchScheduler.rarity()` allocates `Int32Array(total)` —
4 MB per log, 32× the bitfield — and scans all 2^20 indices, and `pump()` allocates a fresh
`Bitfield(total)` per replica-less log on every call.

Measured through the real `Syncer`: one 5,123-byte HAVE_ADD carrying 256 pairs at
`seq = MAX_SEQ` costs 57 ms on the first pump and 7–12 ms after. Add one 5,123-byte NOBLOCK
naming the same pairs — `#recvNoblock` forgets any pair, asked-for or not — and **every `pump()`
costs 1.34–1.43 s on a laptop**, roughly 2.5 s on the tablet by this document's own 1.8× ratio.
`pump()` runs on a 25 ms interval *and* on every inbound frame. One authenticated member, two
frames, and the spore is frozen for as long as they stay connected. Nothing counts it, bounds
it, or closes the hypha.

This is the same shape as the bound that preceded it, and the test gap is this project's
signature: one test drives `seq = 2^32-1` (rejected at decode) and another asserts the Bitfield
product, and neither drives `seq = MAX_SEQ` through `pump()`. It is also honest-scale debt —
50K blocks × 20 peers is ~1M bit-tests per log per pump, and `scheduler.js` already concedes
the quadratic in a comment.

**2. Unlinked bytes are outside the byte budget entirely.** `forgetOldest` iterates
`[floor, linkedTo)`, so anything not yet linked is unevictable and uncounted, and
`sync.test.js` asserts `bytes > budget` as the *correct* outcome. Push blocks at seq 1..N in
your own log and never seq 0: nothing links, so nothing is evictable, and `#trim` exits over
budget having freed nothing. Reachable today by any authenticated peer, and the honest
late-joiner shape hits the same code.

**On the late joiner, an honest scale note.** `MAX_BYTES` is substrate-wide, so no eviction
happens anywhere until a spore holds 64 MiB — for text messages that is ~150–220K messages
colony-wide. The joiner fails only once every reachable peer has lost seq 0, and since they all
run the same budget and see the same traffic they lose it together. So the gate is colony
lifetime volume, not one unusually forgetful member. Latent for SP1 text; real the day inline
media or a smaller phone budget ships.
